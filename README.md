# StudyPad · 英语精读手账

上传任意格式的英语材料 → 按你的目标水平（高中 / 四级 / 六级 / 考研 / 雅思 / 托福）  
自动「涂改」标注 → 一键导出手账。

> **同一篇文章，选不同水平，得到完全不同的两份材料。** 这是本产品的核心。

## 快速开始

```bash
# 1. 安装依赖（已配置独立 venv）
python -m pip install -r backend/requirements.txt

# 2. 构建词表与词频索引（首次必做）
python scripts/build_wordlists.py     # 六档词表，需要 vendor/english-vocabulary-master
python scripts/build_freq.py          # 词频索引，需要 vendor/google-10000-english-master
python scripts/build_general_dict.py  # 六档之外的补充词典 → data/dict/general.json
python scripts/build_ecdict_supplement.py  # 精筛 ECDICT → data/dict/ecdict.json
python scripts/build_lexicon.py       # 全量兜底词典 → data/dict/lexicon.sqlite（约 37 MB）

# 3. 启动
cd backend && python -m uvicorn app.main:app --host 127.0.0.1 --port 8300
```

> `build_lexicon.py` 是**兜底那层**，不做也不会报错，只是生僻词那一行会继续空着；
> 数据来源与许可见 [`data/dict/NOTICE.md`](data/dict/NOTICE.md)
> （**不含柯林斯**：Collins 是 HarperCollins 的商业版权产品，没有免费许可）。

打开 <http://127.0.0.1:8300> ，选择水平 → 上传文件或粘贴文本 → 生成手账 → 导出 PDF。

> **⚠ 在本会话里重启，必须用 Bash 工具的「后台运行」，不能用 PowerShell 工具。**  
> 工具会话结束时会把**整个进程树**收掉 —— `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`  
> 只能脱离控制台，逃不出 Job Object（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）。  
> 所以 `scripts/restart_server.py` 拉起的服务**活不过当前那次工具调用**：  
> 它自己轮询端口时明明 `LISTENING` 成功、退出码 0，下一次调用去探却什么都没有，  
> 日志里也没有任何崩溃痕迹（无 traceback、无 `Shutting down`）——  
> 极易误诊成「服务自己退了」。正确姿势：
>
> ```bash
> cd /f/英语学习应用 && echo "===== restart $(date) =====" >> out/_server.log && \
>   "C:/Users/刘永键/.workbuddy/binaries/python/envs/default/Scripts/python.exe" \
>   -m uvicorn app.main:app --host 127.0.0.1 --port 8300 --app-dir backend \
>   >> out/_server.log 2>&1
> ```
>
> 后台任务由 harness 托管，实测跨大量工具调用稳定存活。  
> 顺带一个反直觉的发现：服务由 Bash 后台任务拉起后，PowerShell 工具的进程  
> **也能连上** `127.0.0.1:8300` —— 所以「沙箱一律连不上回环」并不准确，  
> 真实情况与「谁拉起的服务、谁去连」有关。  
> `scripts/probe_server_alive.py` 可随时确认端口状态与进程 PID。
>
> `scripts/restart_server.py` 仍有价值：它能**杀旧进程 + 确认端口已释放**  
> （本机 PowerShell 工具调 `netstat | Select-String` 会被沙箱拦，  
> `cmd.exe` / `wmic.exe` 又在安全策略黑名单里，拿不到端口和 PID），  
> 只是不要指望它拉起的服务能活过本次调用。

> **`build_general_dict.py` 不能跳过。** 一篇文章里的「超纲词」有相当一部分  
> 根本不在六档词表里（`policymaker`、`healthcare` 这类），没有补充词典的话，  
> 生词表里那些行的音标 / 词性 / 释义 / 例句**全是空的**。  
> 没跑它不会报错，只会静默降级 —— 所以换机器时必须补上这一步。  
> 想确认是否就绪：`/api/health` 返回的 `wordlist` 里有 `general_dict` 标记，  
> 或看生词表有没有整列空白。

支持上传：**文字层 PDF · 扫描件 PDF · 拍照/截图（PNG/JPG/WEBP/BMP/TIFF）· DOCX · Markdown · TXT**。

> OCR 引擎（RapidOCR）首次调用时会自动下载模型权重，之后常驻内存。  
> 没装 OCR 依赖也不影响其它格式 —— 页面顶部会明确提示当前 OCR 状态。

**离线命令行跑通（不启服务）**：

```bash
python scripts/run_pipeline.py cet4          # 输出 out/handbook-cet4.html
python scripts/smoke_api.py                  # 接口冒烟测试（需先起服务）
python scripts/check_render.py               # 渲染产物结构自检
```

**改动之后一次跑全**（22 项 = 20 个单项 + 2 条有序链；含视觉核验；  
必须用装了依赖的那个解释器）：

```bash
<venv>/Scripts/python.exe scripts/run_all.py
cat out/_all_summary.txt                     # 汇总表；失败项的末 400 字详情也在里面
```

一条命令的意义在于：「加了一个新自检但忘了跑」和「漏跑某一项却以为跑全了」不会再发生。

其中「留白视觉链」是**有序**的 5 步（造长文 → 生成修复前/后两份产物 → 量像素 → 导出 PDF 量分页）。  
它验的是断言验不到的东西：**产物结构对了，不等于用户肉眼看到的对**。  
找不到 Chrome 时这一链会跳过（不算失败），其余项照跑。

> **接口测试不一定打真服务。** 本机工具进程的沙箱会把出网强制走代理  
> （`http_proxy=127.0.0.1:<随机端口>`），于是直连 `127.0.0.1:8300` 超时、走代理 502 ——  
> 而服务其实好好地在 LISTENING。以前 `run_all.py` 会因此把两项接口测试判成  
> `SKIP（服务未启动）`，正是「端口探不到就跳过」的假跳过。  
> 现在 `scripts/_api.py` 决定传输：**能连真服务就打真服务**（`STUDYPAD_API` 可指定地址），  
> 连不上退回**进程内 ASGI**（不开 socket），并在汇总表首行打出实际走的那条。  
> 进程内这条路**验不出「服务还挂着旧模块」**，所以改完代码仍要 `restart_server.py` 再看。

### ⚠ 端点一律写同步 `def`，不要写 `async def`

这条不是风格偏好，是**会让服务假死**的硬约束。

本项目的端点里全是**同步阻塞**调用：`httpx` 打模型最长等 90 秒、OCR 推理要数秒、  
词法分析是 CPU 密集。FastAPI 对 `async def` 的处理是**直接在事件循环上执行**（不是丢线程池），  
所以只消一个这样的端点，一次慢请求就能把**整个服务**冻住 —— 首页、其它接口全部排队。

它踩过并且很难查：进程好端端地在 8300 上 `LISTENING`，`netstat` 一切正常，  
日志里最后几条还是 `200 OK`，但**任何请求都不再返回**（客户端只能等到读超时）。  
「端口通、接口不通」看着像网络问题，实际是事件循环被一个请求占死了。

改法是写 `def`，让 Starlette 把请求丢进线程池。  
唯一的代价是同步函数里不能 `await`：`/api/analyze` 里用 `file.file.read()` 取代 `await file.read()`。

```bash
python scripts/test_concurrency.py           # 需先起服务；两层断言把这个坑钉死
```

它既静态遍历路由表（不许出现协程端点），也动态验证：起一个「只收不回」的假上游，  
真发一个会长时间悬挂的请求，同时打普通接口 —— 要求它们仍在毫秒级返回  
（实测基线 13 ms，慢请求在飞时 12–38 ms；若事件循环被占死，这里会退化成数十秒）。

## 它做什么

| 标注         | 视觉           | 判定逻辑                       |
| ---------- | ------------ | -------------------------- |
| **本级考纲词**  | 黄色荧光笔        | 在本级词表内，且通用词频低于本级地板         |
| **超纲常见词**  | 红色手绘圈        | 超出本级范围，但在 2+ 档词表出现 → 最该优先背 |
| **超纲生僻词**  | 天蓝虚线         | 超出本级范围且冷门，认识即可             |
| **六档之外**   | 天蓝虚线         | 六档词表全都没有 → 更高阶词汇           |
| **语法结构**   | 彩色下划线 + 右侧批注 | 9 类结构，按等级给四档深度的中文讲解        |
| **作文加分句型** | 红色波浪线 + 便利贴  | 12 类句型库，注明适用场景 + 仿写示例      |
| **长难句**    | 红色边框         | 超出等级句长阈值，提示先找主谓宾           |

**不配置任何大模型也能完整出稿**——标注部分全部由本地规则引擎驱动。  
配置后，模型只负责把语法讲解重写得更自然（`llm.py`，OpenAI 兼容协议）。

> **唯一的例外是中文译文**：自然流利的中文没法靠规则拼出来（词对词拼接只会读成乱码），  
> 所以译文**必须**走大模型。没配模型时不会有译文，但会明确告诉你原因，  
> 而不是塞一份读着像中文、其实是乱码的「假译文」——那比不给译文更糟。

## 进度反馈：为什么不是「一直转的圈」

第一版生成时只有一个转圈的按钮，写着「正在标注…」，旁边还并排着一句  
「准备就绪，点击「生成手账」」—— 用户既不知道它在干什么，也不知道**是不是卡死了**。  
更糟的是这句话**把等待的原因说错了**：标注本身是纯规则、毫秒级，  
真正耗时的是 OCR 和等模型，所以「正在标注…」恰好掩盖了那两件真正在等的事。

现在生成时会出现一条真实进度条：阶段名 + 百分比 + 阶段内的明细 + 已用时长。

### 三条原则

1. **不编进度。** 百分比只在**有分母**的地方推进：知道要翻几批就用批次做分母  
   （「已翻译 2/3 批」），知道有几页就用页数做分母（「OCR 识别第 1/2 页」）。  
   分母未知的阶段（等模型应答）**不动进度条**，改为如实显示「在等什么」。
2. **百分比单调不减。** 回退会让人以为出错了 —— 那比没有进度条更糟。  
   实现上记住历史最高点（`max_percent`），乱序上报也不会让它倒退。
3. **上报绝不拖慢主流程。** 上报只是内存字典 + 一把锁，任何异常都吞掉；  
   轮询失败在前端也静默 —— 进度条是**增强**，不是请求成功的前置条件。

### 等待文案必须跟着阶段走

卡住超过 6 秒（`progress.STALL_AFTER`）会切到琥珀色条纹并显示「在等什么」。  
这句文案**逐阶段写死在 `progress.plan()` 里**，不能用一句通用的「等待模型应答」兜底：

| 阶段         | 卡住时显示                               |
| ---------- | ----------------------------------- |
| 解析（含 OCR）  | 正在 OCR 识别扫描件（每页约 1–2 秒，照片大或页数多时会更久） |
| 标注         | 正在用本地规则引擎标注（纯本地计算，不需要联网）            |
| 大模型讲解 / 译文 | 等待模型应答，正在整批翻译（大模型一般需要数秒到一分钟）        |
| 排版         | 正在排版手账                              |

OCR 是本地推理，一页照片跑十几秒很正常，那时说「在等模型」就是把原因讲错了 ——  
和原来那句「正在标注…」属于同一类毛病。  
另外「已用时 N 秒」这个时钟**始终在走**，时长本身就是「没卡死」的证据。

### 接口

| 接口                           | 说明         |
| ---------------------------- | ---------- |
| `GET /api/progress`          | 任务表统计（排查用） |
| `GET /api/progress/{job_id}` | 进度快照       |

`job_id` 由前端生成、随生成请求一起提交（表单字段 / JSON 字段，**可选**）。  
未登记的任务返回 `200 + {"found": false}` 而**不是 404** —— 轮询一个还没建好的任务  
是正常情况，不该让浏览器控制台刷满错误。

```bash
python scripts/test_progress.py        # 模块层 + 真实 HTTP + 真实并发（含真实 OCR）
```

它验的不是「数据结构算得对」，而是**用户会看到的那个序列**：百分比单调、  
阶段按序推进、模型卡住时出现等待提示、失败时立刻停轮询并给出原因。  
其中「OCR 停顿时不能说成在等模型」这条，靠临时把 `STALL_AFTER` 压到 0.6 秒  
**强制触发** —— 真实 OCR 每页之间有上报，按默认阈值常常不会触发，  
靠碰运气等于没验。

## 大模型接入

支持 DeepSeek / OpenAI / 通义千问 / 智谱 / Kimi / Groq / 本地 Ollama / 任意 OpenAI 兼容端点。

### 两套模型，各干各的（翻译 ≠ 讲解）

从 2026-10-15 起，**「生成手账内容」和「翻译」是两个可以分开配置的模型**：

| | 干什么 | 默认走哪 | 为什么 |
|---|---|---|---|
| **大模型**（`llm_*`） | 重写语法讲解、生成考点 brief | 云端 API（DeepSeek 等） | 需要真正的语言理解 + 考纲上下文，小模型干不了 |
| **翻译模型**（`mt_*`） | 只做中英翻译 | **本机 Ollama 的 `hy-mt2:1.8b`** | 逐句转写、量大、不需要智能；本机跑不花钱也不慢 |

分开的实际意义：

- **速度**：一篇 23 句的文章，云端逐句翻要几十秒，本机翻译模型 **3.3 秒**翻完（11.5k 字符的长文 15.5 秒）；
- **额度**：翻译不再消耗云端 token。实测同一篇 23 句文章翻译本身用了 1.7k tokens，
  这些现在全部由本机承担（云端额度只留给讲解）；
- **不依赖**：**没配任何云端 Key 也能出译文** —— 翻译只认 `mt_*`。
  反过来，云端 Key 失效时讲解会降级为纯规则标注，**译文照样有**。

设置页里两套配置各有各的下拉框、字段和「测试连接」按钮，互不影响。
翻译模型有两个开关：

- **翻译交给这个模型**（默认开）：关掉则退回用上面的大模型翻译（更慢，且按 token 计费）；
- **它连不上时自动退回大模型翻译**（默认开）：不勾则宁可这一篇不出译文，也不偷偷花额度。

> 生成前会先对翻译模型做一次 1 token 的探活。理由：本机端点不需要 Key，
> `ready` 判断对 localhost 一律放行 —— **Ollama 没启动时它照样「就绪」**，
> 不探活的话整篇翻译会按 4 路并发发出去、各自等到超时，用户看到的是「卡两分钟然后没有译文」。
> 探活失败会按上面两个开关决定退回大模型还是如实报「翻译不可用」，并把原因写进手账的 `trans_note`。

> **配置一次就够，下次打开不用再填。** 填好 Key 点「测试连接」，  
> 通过即自动保存到本机 `~/.studypad/settings.json`  
> （Windows 上是 `C:\Users\<你>\.studypad\settings.json`）。  
> 之后每次生成自动取用，页面顶部会显示「已保存：deepseek（sk-\*\*\*\*\*\*3f9a）」。  
> 想换 Key 直接填新的覆盖，想清空点「清除已保存配置」。

安全约定：

- **配置文件放在用户目录，不在项目目录里** —— 拷贝、打包、开源这个项目都不会带走你的 Key。
- **Key 不回传浏览器**：接口只返回 `sk-******3f9a` 这类掩码，生成时由服务端直接取用，  
  前端全程不持有明文 Key，也不写 localStorage。
- 配置文件在本机是**明文**（单机应用没法真正藏住本地密钥），多人共用一台机器时请留意；  
  想换存放位置，设环境变量 `STUDYPAD_HOME` 即可。
- 本地 Ollama 不需要 Key，不会被误当成「已保存的云端配置」而回退。

成本控制：本地规则引擎先筛出值得标注的句子（约占全文 35–50%），  
只把这些句子送模型，且**只用来重写讲解，不让模型决定标什么**。

> **用推理模型（如 `deepseek-v4-pro`）的话，注意它会先把输出预算花在思考上。**  
> 本项目的讲解与翻译都不需要推理，所以调用时默认带 `thinking: {"type": "disabled"}` 关掉它；  
> 若你的网关不认这个字段，程序会自动去掉重发一次（并记住这家不吃这套），不会因此报错。  
> 想反过来让模型思考，设 `STUDYPAD_LLM_THINK=1`。  
> 排查接口问题时设 `STUDYPAD_LLM_DEBUG=1`，会把每次调用的 token 用量写到 stderr。

## 中文译文

生成手账时可以顺带把原文译成自然流利的中文，两种版式可选：

| 版式       | 呈现               | 适合           |
| -------- | ---------------- | ------------ |
| **逐句对照** | 每句原文下面紧跟这句的译文    | 精读、逐句抠意思     |
| **整段附译** | 原文整段保持完整，译文挂在段落下 | 先读完整段，再看整体理解 |

默认按等级给：高中 / 四级开，六级及以上默认关 ——  
低阶段靠全译建立理解，高阶段要练的是「不依赖译文也能读懂」，需要时手动勾上即可。

### 三条不妥协的设计

**1. 没有规则兜底，没模型就没有译文。**  
规则引擎能做的「翻译」只是词对词拼接，读出来是乱码，会让人误以为自己读懂了。  
所以未配置模型时不做任何降级编造，而是明确说明「翻译必须由模型完成」，  
并给出两条路：装本机翻译模型（默认，见上一节），或把「翻译模型」指向任意 OpenAI 兼容端点。

**翻译由哪个模型做，是可以单独配的。** 默认是本机 Ollama 上的 `hy-mt2:1.8b`（Apache-2.0，1.8B），
它只干翻译这一件事；手账讲解仍走云端大模型。两者互不兜底：

- 关掉本地翻译（「翻译交给这个模型」取消勾选）→ 退回用大模型翻译，并在译文说明里写明「本次消耗主模型额度」；
- 本机模型连不上且勾了「自动退回」→ 退回大模型并写明「本次已退回」；
- 两边都不可用 → 如实报「翻译不可用」并给出原因，**不会糊一份假译文**。

手账返回里有两个机器可读字段说明「谁干了什么」：`llm_model`（讲解）与 `mt_model`（翻译），
自检与前端都据此断言，不必去解析中文说明文案。

**2. 对齐错了比不翻更糟。**  
译文挂错句子会直接误导阅读理解。所以：

- 分句用 `analyzer.split_spans()` 给出**精确字符区间**，`end - start == len(句子)` 且相邻不重叠 —— 逐句渲染和译文挂载都靠它，错位比不翻译更糟；
- 每批请求做「返回条数必须等于输入条数」的硬校验，对不上就带着「上次给了几条」重试一次；
- 重试仍对不上就把这批**拆成两半各试一次**（`MAX_SPLIT_DEPTH = 1`），  
  把答不好的那一句隔离出来，同批里本可以翻好的句子保住；
- 连拆两半都不行就**整块放弃**，在结果里报告「N 处对齐失败，为避免译文挂错句子已整段跳过」；
- 一段里只有部分句子译出时，整段译文留空并标 `partial`（渲染为琥珀色），  
  绝不拿残句拼成一段让人以为翻全了。

**3. 缓存按句子哈希，不按等级。**  
同一篇文章在六个等级之间来回试标注时，译文直接复用 ——  
否则用户每换一次等级就要重付一次翻译费。缓存目录 `~/.studypad/trans_cache/`（上限 400 条，按最近使用淘汰），  
前端有「清空译文缓存」按钮。

### 为什么它不慢（以及踩过的一个推理模型陷阱）

一篇 23 句的文章，最初要 **94 秒**，现在 **不到 3 秒**。差距几乎全部来自下面四件事：

**1. 推理模型会先把钱花在思考上。** `deepseek-v4-pro` 这类推理模型先产出 `reasoning_content` 再产出  
正文。实测翻 18 句的一次调用：`completion_tokens=2710`，其中 **`reasoning_tokens=2439`（90%）**，  
正文只写了 271 个 token —— 预算被思考吃穿，`content` 直接是**空字符串**。  
下游看不出真因，只能判成「条数对不上」→ 重试 → 二分救援，一次调用膨胀成四次，还丢掉一整段译文。  
→ 翻译是纯转写任务，不需要推理，所以默认发 `thinking: {"type": "disabled"}` 关掉它  
（网关不认这个字段时会自动去掉重发一次，并记住这家不吃这套）。  
这是**双保险的另一半**：输出预算也按 3 倍估（`min(4000, 400 + 3×字符)`），  
即使关不掉思考也不会被吃穿。空正文还会按真因分三种报错（推理吃穿 / 被截断 / 真空回复），  
不再糊成一句「未返回可解析的 JSON」让人无从下手。

**2. 批次并发发。** 各批之间本来就互不依赖（合批只影响 token 效率，不影响正确性），  
串行时整篇耗时等于各批耗时**之和**，并发后等于**取最慢那批**。实测 4 批：  
串行 93.96 秒 → 并发 2.82 秒。

**3. 批小一点反而更快。** 单批耗时几乎全来自模型生成输出，而输出长度与批大小成正比。


批小 → 单批快（并发时总时长取最慢那批）、更容易对齐、万一失败二分也更便宜；  
代价只是多几次请求，而系统提示词有前缀缓存（实测 `prompt_cache_hit_tokens ≈ 600`），多出来的开销很小。

**4. 共用一条 HTTP 连接池。** 每次调用重做一遍 TCP + TLS 握手，在小批多请求下是纯浪费。

进度条也因此变得有意义了 —— 它是按**批**推进的，而不是一路空转：

```
0/4  准备并发翻译 4 批（4 路）        t=0.0s
1/4  已完成 1/4 批，还在等其余批次     t=1.2s
3/4  已完成 3/4 批，还在等其余批次     t=2.6s
4/4  已完成 4/4 批                    t=2.8s
```

### 成本护栏

| 护栏     | 值                       | 说明                                                        |
| ------ | ----------------------- | --------------------------------------------------------- |
| 整篇字符上限 | 24000 字符                | 约 8 页 A4；超出部分不译并在结果里标注「原文超长」                              |
| 单请求句数  | 8 句                     | 跨段落合批，一段一句的文章也不会变成一次一句地发请求                                |
| 单请求字符  | 800 字符                  | 防止单个超长段落撑爆单次请求                                            |
| 并发路数   | 4                       | `STUDYPAD_TRANSLATE_WORKERS` 可调（1–16）；多数服务对并发请求数有限制，故保守取值 |
| 单批输出预算 | `min(4000, 400 + 3×字符)` | 按 3 倍估，是为了盖住推理模型的思考开销                                     |
| 分句缓存   | 命中即 0 成本                | 重发同一篇、换等级、换版式都不产生新请求                                      |

翻译关掉时**一个字都不会加**：接口会拿同一篇文章开/关各跑一遍做回归，标注计数与分块内容必须完全一致 ——  
翻译是旁路，一旦它改动了 block 内容或顺序，标注就会跟着漂。

### 前端的静默失效

前端是单文件内联 JS，改完之后只有「打开浏览器点一遍」才能发现问题，  
而下面三类错误都**不报任何错**，只是功能悄悄不生效：

```bash
python scripts/check_inline_js.py      # 语法 + id 交叉校验 + class 交叉校验
python scripts/probe_css_check.py      # 验证上面那两项校验真的会拦错（不是恒真）
```

1. **语法错误** —— 整块脚本跑不起来（交给 `node --check`）。
2. **id 写错** —— `$('progBar')` 取到 null，要么当场抛错，要么被 `if (el)` 兜住后永远不生效。
3. **class 写错** —— `setProgressClass('prog waiting')` 里的类名没有对应 CSS 规则时，  
   元素还在、样式也对了一半，看着就像「能跑」，只是等待时的琥珀色条纹不出来。

第 3 条依赖一条**命名约定**：函数名以 `Class` 结尾 ⇒ 它的字符串参数会直接赋给 `className`。  
改了名字校验就覆盖不到那个分支（所以函数定义处也写了注释提醒）。

`probe_css_check.py` 是给上面这个检查做的探针：把 `'prog waiting'` 改成 `'prog waitng'`、  
或删掉 `.prog.waiting` 的 CSS 规则，检查**必须报错**。  
这不是多此一举 —— 探针第一次跑就抓出两个真问题：`class="..."` 的正则把内联 JS 里的  
`'<span class="' + esc(...) + '"` 也匹配进来了（干净文件被误判成有问题），  
以及只认 `className = '...'` 赋值导致 `setProgressClass('prog waiting')` 那一处**漏检**。

## 留白：一个被误读了两次的问题

用户反馈「生词表上面有很长的留白」，并补充「说的是**绿色译文框没有翻译下文**，  
这一页是翻译失败的一页，可能留白分页了」。

这个 bug 查起来绕，因&#x4E3A;**「留白」是四种不同成因叠在同一个视觉症状上**，  
而且我第一遍就误读了（以为指生词表**内部**有空行）。逐一钉死之后是这样：

| # | 成因                                   | 视觉表现                          | 修在哪                                          |
| - | ------------------------------------ | ----------------------------- | -------------------------------------------- |
| ① | **译文内容本身是零宽 / 空白字符**                 | **绿色**框（`.tr-zh`）有背景、一个字都没有   | `render._visible()` + `parsers.clean_text()` |
| ② | **逐句产出「（本句未译出）」占位框**                 | **黄色**框（`.tr-zh.partial`）成排出现 | `_render_block_sentence` 不再逐句配框              |
| ③ | **`.block{break-inside:avoid}` 一刀切** | 打印时整页尾部空掉 = **留白分页**          | `@media print` 只对小元素禁止断开                     |
| ④ | **失败没有任何提示**                         | 用户只看到空框，不知道发生了什么              | 顶部 `.hb-note` 降级提示条                          |

### ① 零宽字符能骗过 `str.strip()`

PDF 文字层与 OCR 里很常见 `U+200B`、`U+FEFF`、`U+200C/200D`、`U+2060`，  
它们**全都通过 `str.strip()`**。于是「整块只有零宽字符」的伪区块被当成有内容渲染，  
页面上就留下一个占着位置、却一个字都看不见的框。

判空必须走 `_visible()`（删零宽 + C0/C1 控制字符后再 strip），**不能用 `str.strip()`**。  
解析层 `parsers.clean_text()` 再从源头清一遍 —— 它现在也清控制字符，  
因为 PDF 文字层里的 `\x00`、`\x0c` 同样骗得过 `strip()`。

> 这条路径也解释了用户那张截图：他看到的**绿色**框里一个文字像素都没有。  
> 而②的占位框是**黄色**的（`.tr-zh.partial` 把 `border-left-color` 换成了 `#e8c979`）——  
> **颜色本身就是线索**，绿色 = 有译文记录但内容不可见，黄色 = 明确的「没译出」标记。

### ② 口径不一致：一个按「成功句」存，一个按「全部句」遍历

`translate_blocks` 第三趟只把**成功译出的句子**放进 `tr["sentences"]`（并置 `partial=True`），  
而 `_render_block_sentence` 是按**全部 span** 遍历的。旧实现在「这句没有译文」时  
也产出一个 `<div class="tr-zh partial">（本句未译出）</div>` ——  
于是一页里几段部分失败就堆出十几到几十个空占位框。

现在的规则：

- 整段**一句都没译出** → 完全退回「原文照排」，一个框都不出；
- 部分译出 → 只给真的译出来的句子配绿框，没译出的**只排原文不配框**，  
  末尾用**一条**灰色 `.tr-miss` 说明丢了几句（N 个框 → 1 行字）。

### ③ 留白分页的正解：只在「注定装得下」的元素上禁止断开

逐句对照的块（`.tr-sent`）动辄比一整页还高。`break-inside:avoid` 加在它身上，  
浏览器无法既避免断开又放下它，只好**整块推到下一页** —— 前一页尾部就空一大片。

```css
.block{break-inside:auto}                 /* 整块允许断，把每页填满 */
.block.title,.block.heading{break-inside:avoid}
.tr-pair{break-inside:avoid}              /* 句对不拆：不会「原文在这页、译文在下页」 */
.note,.tr-zh,.tr-miss{break-inside:avoid} /* 便利贴不拆：半张跨页很难看 */
```

实测（长文夹具，`probe_pagination.py` 真导出 PDF 逐页量）：

|     | 总页数      | 留白页（非末页正文 < 60% 页高）  | 末页外最大尾部空白      |
| --- | -------- | -------------------- | -------------- |
| 修复前 | 24 页     | **4 页**（正文只到 28% 页高） | 909px（≈72% 页高） |
| 修复后 | **17 页** | **0 页**              | 172px          |

### ④ 覆盖率必须**按句**算

只按「段」算会漏报：一段里丢 2 句、剩 1 句译出来，段覆盖率照样 100%，  
而用户正在读一段缺了三分之二译文的文章。所以页眉报 `中文译文 7/13 句`，  
覆盖不足时 chip 转告警色、顶部出 `.hb-note`。覆盖完整时不出提示条（保持页面干净）。

参考：`render._has_zh()` 判的是「这条记录**真的有字**」——  
不能写 `if tr`，空壳记录 `{"zh":"","sentences":[]}` 存在但渲染不出任何框，  
按记录条数算会高报成「4/4 段」。

### 怎么验的

```bash
python scripts/run_all.py                    # 第 4、5 步就是这条链
```

`make_trans_fail_demo.py` 把同一份「部分翻译失败」的语料分别喂给**旧实现**与**新实现**  
（旧实现是脚本里内联的一份 `_old_sentence`，同时把打印 CSS 也换回旧版 ——  
否则「修复前」会悄悄享受着新 CSS，对照就被混淆了），各出一份 HTML：

|     | 绿框（真译文）   | 黄框（占位）               |
| --- | --------- | -------------------- |
| 修复前 | 12 条，条条有字 | **11 条**（每框 96 文字像素） |
| 修复后 | 12 条，条条有字 | **0 条**              |

**像素探针踩过的坑（值得留个记录）**：第一版按 `.tr-zh` 的**底色** `(238,242,234)` 找框，  
容差 6。但纸面每 32px 有一条横线，它**透过半透明绿底**叠出来的颜色是 `(220,228,228)`  
（差 18/14/6），直接判成「不是绿框」—— 于是一条 40px 的译文带被切成  
「28px 有字 + 12px 没字」两片，每次都多报 5~6 条假空带。  
**正解**是认那条**不透明**的 `border-left`（`#9dc7bd`），不受底色纹理干扰。

## 生词表：为什么以前有一整列是空的

用户反馈「生词表里的单词内容不完整，请补全每个单词的意思和词性以及音标」。

根因是 `wordlist.entry()` 的注释写着「按高→低逐档回退」，实现却是  
`for i in range(start, -1, -1)` —— **只搜本级及更低档**。而文章里的「超纲词」  
恰恰多数在**更高**档（`artillery` 在 cet6/ielts，`oath` 在 cet6/kaoyan/ielts），  
于是一个都取不到，生词表那一行只剩一个小圆点 + 一个来源标签。

现在的查询策略是**候选词形优先、档位次之**，五层兜底：

1. **词形候选 × 全部六档**（`_search_order` 覆盖本级 + 更低档降序 + 更高档升序）。  
   顺序不能反 —— 先档位后候选会在 high_school 档里拿 `caption` 的词条去解释 `captive`。
2. **字段级补全**（`_fill`）：命中一条**缺音标**的记录（六档里有 571 条 `p` 是空串）时，  
   从其它档位/补充词典把**空字段**填上。只填空字段，绝不覆盖已有值 ——  
   已有的 `t` 是该档位首选义项，自带档位语义，不能被别档盖掉。
3. **补充词典** `data/dict/general.json`（`build_general_dict.py` 生成）：  
   同源词库里**六档之外**的 8319 个词，跳过六档已有的 13354 词。
4. **精筛 ECDICT** `data/dict/ecdict.json`（`build_ecdict_supplement.py` 生成）。
5. **全量兜底库** `data/dict/lexicon.sqlite`（`build_lexicon.py` 生成，**349,713 条**）。  
   见下一节：前面几层都是预先筛过的小子集，兜不住文学/旧文本里的词。
6. **复合词拆分**（`_compound_entry`，最后手段）：  
   `policymaker` 词典里没有，但 `policy` + `maker` 都有 → 释义写成 `政策 + 制造者`，  
   并在 `e` 里注明「复合词，由 policy + maker 合成」、标 `c=1`。  
   要求 8 ≤ 长度 ≤ 20 且两半都是 ≥4 字母的实词（否则 `there` 会被拆成 `the` + `re`）。  
   **宁可让用户自己把两半拼出语义，也不编一个「政策制定者」出来** ——  
   编出来的释义没有出处，错了没人发现。  
   （带连字符的词若在全量兜底库里有词条，就用词条本身、只把缺的音标/词性按两半补上，
   不会再拆成「A + B」那种拟造释义。）

派生与拼写变体（`lemmatize.py`）另加两组规则：`-ive ↔ -ion`（`convulsive → convulsion`）。  
英式→美式拼写（`-ise→-ize` / `-our→-or` / `-re→-er`）**必须放在候选表最后**：  
这些规则会误伤同形的真词（`promise→promize`），但只要原词本身能命中就不会走到那里 ——  
**顺序即安全边界**。

实测六档生词表的字段覆盖率（`samples/sample_article.md`）：

| 档位          | 生词 | 音标 | 词性 | 释义 | 例句 |
| ----------- | -- | -- | -- | -- | -- |
| high_school | 20 | 20 | 20 | 20 | 20 |
| cet4        | 15 | 15 | 15 | 15 | 15 |
| cet6        | 9  | 9  | 9  | 9  | 9  |
| kaoyan      | 7  | 7  | 7  | 7  | 7  |
| ielts       | 5  | 5  | 5  | 5  | 5  |

验证：`probe_compound.py`（复合词、反向「短词不许被拆」、派生回归、字段补全收益、六档覆盖率）

- `verify_render_api.py`（真服务端到端，断言生词表每一行都有四项）。

## 生词表：为什么有的词显示「词典未收录」

用户反馈「生词表里有的单词信息没有完全显示」，截图里那行是
`anticipation--anticipation` + 音标/词性/释义/例句**四列全空**。

那次查出来是**三个独立的 bug 撞在同一列上**，症状一模一样：

1. **断词正则把 `--` 当成构词连字符**（主因）。`_WORD_RE` 写成
   `[A-Za-z][A-Za-z'\-]*`，允许**任意连续**连字符，于是原文里
   `anticipation--anticipation`（`--` 是 Gutenberg 文本里 em dash 的 ASCII 写法，
   **是分隔符不是连字符**）被吃成一个 token。这一个 token 谁都不认 →
   判成「六档之外」→ 三层补充词典都按整串查不到 → 那一行四列全空。
   改成只允许单个内部连字符（`well-known` 仍正常，`a--b` 拆开），
   回归见 `probe_dash_token.py`。
2. **词形还原只拆一层**：`hootings` 只会被拆到 `hooting` 就停，不再拆到 `hoot`，
   于是「复数 + 现在分词」这种双重屈折全查不到。`_cands()` 加一层回溯展开。
3. **不规则动词表缺口**：补了 31 个书面语高频的过去式/过去分词
   （`smitten/swept/dealt/stricken/trodden…`），判据是「当前认不出 **且** 原形确实在六档词表里」。

修完这三处，那篇文章的生词表从「4 行信息不全」降到「1 行」——
剩下的是 `caisson`：**它在 ECDICT 源数据里音标、中文释义俱全，只因 `bnc=0`
被 `build_ecdict_supplement.py` 的排名闸门筛掉了**。前四层全是预先筛过的小子集，
而这个应用吃的恰恰是 Gutenberg 这类文本，被筛掉的正是这类文本里最需要的词。

所以要了**第五层：全量兜底库**（`data/dict/lexicon.sqlite`，349,713 条）：

- **ECDICT 全量**：放开排名闸门，凡是「有中文释义的纯英文单词」都收
  （纯屈折说明条目 `smite的过去分词` 除外，释义交给词形还原后的原形）；
  词性原来在 ECDICT 里没有独立字段，是从释义行首（`n. 预期, 预料`）解析出来的。
- **CMUdict**（BSD-2）补音标：ECDICT 只有 28% 的词条带音标，ARPAbet 转 IPA，
  沿用项目既有写法（重音 `'` 前缀、schwa 用 `ә`）。
- **Open English WordNet 2024**（CC BY 4.0）补英释与例句 —— 生词表的例句列，
  以前对 ECDICT 来源的词基本是空的。

渲染也随之改成**英汉双解**：中文释义在上，英释压暗小一号另起一行；
两样都没有才写「词典未收录」（灰色斜体，读起来像注解而不是释义）。

实测（`a-mystery-of-heroism`，4175 词）：生词表 85 行，
**音标/词性/释义空行 0**（此前 4 行不全），22 行带英释、80 行带例句。

> 数据来源与许可、以及**为什么不能内置柯林斯**，见 [`data/dict/NOTICE.md`](data/dict/NOTICE.md)。
> 简言之：Collins COBUILD 是 HarperCollins 的商业版权产品，没有免费许可，
> 网上流传的 MDX/StarDict 版本都是未授权转载，不引入。
> ECDICT 里的 `collins` 列只是**柯林斯星级**（1~5 星难度标记），不是释义内容。

已知取舍：生词表**按原形归并**（`convulsive` 与 `convulsion` 并成一行、用后者的词条），
所以派生词显示的释义词性可能与文章里的词形不一致（`stolidity` 显示 `stolid` 的形容词释义）。
试过让「词本身有词条就直接用它的」优先，但那会同时改掉档位与补充词典的优先级，
影响全站每个派生词的解析，风险大于收益，故维持原形归并。详见 NOTICE 末节。

## 黑色横杠：产物是对的，但交付方式脆弱

用户第三次反馈：「为什么会有黑色横杠」——截图里 `stripped` / `emerges` 两个词的**下半部分**  
各压着一块**实心纯黑矩形**，文字在黑块里完全看不见。

先说结论：**我这边同一条 HTML 渲染出来是 0 条纯黑、1700+ 像素荧光黄**（无头 Chrome 截图），  
**导出的 PDF 也是 0 黑条、1150+ 像素荧光黄**。产物内容、预览服务、`out/*.html` 全部核对过，  
都没有被改写。所以问题不在「写错了什么」，而在**这条 CSS 的两个脆弱点**：

| # | 脆弱点                | 为什么它会变成黑                                                                                                                                                                   |
| - | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① | `--hl` 这种**通用变量名** | 会被宿主环境重定义。**旁证很硬**：同一个 `:root` 里的 `--paper` 完全正常（截图背景 `(252,250,243)` 就是我们的纸色），**只有 `--hl` 变黑** —— 同一个样式表里一半对一半错，只能是外围覆盖了这个名字                                              |
| ② | 渐变里的 `transparent` | 它**不是「无色」，是 `rgba(0,0,0,0)`** —— 黑配零透明。任何丢掉 alpha 的渲染路径都会把它变成**不透明纯黑**。这条路径真的存在：`probe_pagination.py` 量到 Chrome `print-to-pdf` 下所有 `.note` 都是**零面积矩形**，说明它确实会丢元素、会走非标准渲染路径 |

定位方法是纯几何的：黑块位置与 `.w-target` 的  
`linear-gradient(180deg, … 52% … 92% …)` **完全吻合**（正好是词的下半段），  
而全仓库最深的颜色是 `.chip.warn` 的 `#B91C1C`，**根本没有纯黑**。

**两处加固**（都不削弱视觉效果）：

```css
/* ① 变量全部加项目前缀，关键视觉不依赖变量 */
:root{ --sp-paper:#fdfaf3; --sp-hl:#FFE066; --sp-ink:#2b2b2b; /* … */ }

/* ② 荧光笔写死字面量；透明端换成同色族零透明 */
.w-target{background:linear-gradient(180deg,
  rgba(255,224,102,0) 52%, #FFE066 52%, #FFE066 92%, rgba(255,224,102,0) 92%)}
```

第 ② 条的要点：**丢掉 alpha 时得到的是「看不见」，而不是「一块黑」**。  
纸纹那条（`repeating-linear-gradient`）同理，透明端换成 `rgba(120,150,190,0)`。

**回归怎么钉**：`check_render.py` 新增「黑条回归」，写成可复用的 `_audit_pen()`，  
正向 13 条 + **反向 4 条**。反向那 4 条故意把旧实现贴回去 / 把零透明改成不透明黑，  
要求审计**必须报警**（实测分别报出 6 项与 4 项）——  
一条永远不会失败的断言等于没写，这个项目已经被「假绿断言」咬过两次。

## 考点知识库

`backend/app/exam_points.py` 是六档考点的**结构化、可溯源**知识库。  
它回答的是「这个阶段到底考什么」，而且**每一条都能翻到出处**。

覆盖六档 × 五个维度：

| 维度    | 内容                                       |
| ----- | ---------------------------------------- |
| 词汇    | 目标词量、官方口径依据、词量分层、考查侧重                    |
| 语法    | 该阶段真正加权的语法块（高中 10 块 / 四级 5 块 / 考研 5 块 …） |
| 题型与分值 | 逐题的题量、分值、时长、说明；失效旧制单独标注失效日期              |
| 高频考点  | 按主题归纳的高频失分点与解题要点                         |
| 考查重点  | 该阶段最关键的几条结论                              |

规模：**6 档 · 19 条来源（8 条 official）· 33 个语法考点块 · 40 条题型 · 29 个高频主题 · 156 处溯源引用**。

**来源分级**（接口与页面都会把分级露出来，让用户自己判断可信度）：

- `official` —— 考试主办方／教育主管部门原文。例：ETS 官方页面、  
  IELTS 官方 band descriptors、`cet.neea.edu.cn` 四六级大纲、教育部高中课标。
- `semi_official` —— 权威教研机构对官方口径的转述（新东方等）。
- `secondary` —— 第三方整理，仅作旁证。
- `oss` —— 开源侧独立核实，作为第三方面与官方口径互校（见下）。

**开源侧独立核实（`tier=oss`）**。以下几点是把官方口径拿去和独立数据源对照后得到的，  
也是「有据可查」最实在的部分：

| 核对面           | 结论                                                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 考研大纲词表独立核实    | **5,501 条**（含 `a/an` 合并与 5 个英美拼写变体补丁，附 SHA256）                                                                                                               |

> `openetymology/OpenEtymology` 判成 `NOASSERTION` 并报告「无传染性许可」，  
> 但它的 `DATA_LICENSE.md` 明确是 **CC BY-SA 4.0（share-alike）**。

> **时点敏感数据单独标注。** 例：TOEFL 自 2026-01-21 起改为自适应新制

> 1–6 分制）。库内同时保留 2023–2026.1 的旧制条目并标注失效日期 ——

接口：

## 三个曾经「静默失效」的 bug

这一节记的是**不报错、不告警、测试还照样全绿**的那类失效 —— 最难发现，也最值得留档。  
三个都在 2026-10-14 的代码审查里查出并修掉，各配了一条回归断言。

### ① Markdown 的表格/代码块被搬到全文最前

`parse_markdown` 旧实现分两趟：先用一个 while 循环把表格/代码块按文档顺序收进来  
（`order` 从 0 起算），再把「剩下的正文」整批交给 `parse_text`，块号接着往下排，  
最后按 `order` 排序。于是**只要文档里出现一个表格或代码块，它就会被搬到最前面**  
—— 连标题都排到它后面。

实测（修复前）：

```
type 序列 = ['table', 'code', 'title', 'paragraph', 'paragraph', 'paragraph']
```

改成**单趟**后顺序恢复文档原序：

```
type 序列 = ['title', 'paragraph', 'table', 'paragraph', 'code', 'paragraph']
```

回归：`probe_md_order.py`。

### ② 生词表的顺序是乱的

`build_vocab` 旧实现是 `sorted(selected, key=lambda x: x["start"])` ——  
而**每个 block 的 `start` 偏移都从 0 起算**，段与段之间完全分不清先后。  
排序结果既不是文章顺序、也不是任何稳定顺序。实测第 5 段才出现的  
`Policymakers` 排在生词表第 0 位。

改成按 `(block 顺序, 段内偏移)` 排之后，顺序与文章出现顺序严格一致。

回归：`probe_vocab_order.py`。

### ③ 原文带前导空白时，译文会**一个绿框都不出**

最危险的一个。全链路有三处独立调用 `split_spans`，它们必须落在同一套偏移上：

| 调用方                             | 用途                               |
| ------------------------------- | -------------------------------- |
| `annotator.analyze_block`       | 产出标注的 `start` / `end`            |
| `render._render_block_sentence` | 按 span 切原文、挂译文                   |
| `translate.translate_blocks`    | 产出 `sentences[].start`，译文就挂在这个键上 |

旧实现里 `translate` 用的是 `text.strip()` 之后的文本算 span，  
而另外两处用的是**未 strip** 的 `block["text"]`。strip 会吃掉前导空白，  
第二句及以后的起始位置整体前移：

```
未 strip：[(2, 69), (70, 178)]
已 strip：[(0, 67), (68, 176)]
```

于是 render 拿着 `70` 去 `zh_map` 里找、只找到 `68` → **一个绿框都不出**，  
还顺手误报「本段另有 N 句未取到译文」和「中文译文只覆盖 0/N 句」。  
全程不报错，用户只看到「没有译文 + 一串警告」。

修法：`translate` 也改用未 strip 的原文算 span（`strip` 后的长度只用于统计）。  
**铁律：任何新增的「按偏移定位」的代码，都必须用同一个未 strip 的 `block["text"]`。**

回归：`probe_ws_offset.py`（跑真实的 `translate_blocks`，假模型不发请求）。

### ④ 六档参数里有两个「只写不读」的死键

`levels.py` 的设计承诺是「切换等级 = 换一份参数，不改任何代码」，  
前提是每个键都真的接了线。审查发现两个只写不读的键：

- `grammar_density`（0.75 → 0.2）：注释写「每句被语法标注的概率上限系数」，  
  但 `markup.select` 只读 `grammar_max_per_para`。
- `explain`（`zh` / `bi` / `en`）：ielts 声明双语、toefl 声明英文，  
  但 `patterns.py` 的讲解文本**只有中文**，没有可显示的英文内容。

这两个都需要产品决策（补英文讲解，还是把配置改回 `zh`），  
所以没有偷偷改数据撒谎，而是**登记在案**：  
`scripts/probe_level_config.py` 会把「声明了但没被读过」的键挑出来，  
**不在 `KNOWN_GAPS` 表里的新死键会让回归直接红**。

## 一个 500 把病因藏起来的两层bug（2026-10-15 用户截图反馈）

用户截图里的报错是：

```
Unexpected token 'I', "Internal S"... is not valid JSON
```

这句话**不是病因，是第二层故障**。往上追有两层，两层都修了。

### 第一层：服务端真的 500 了

追 `out/_server.log` 的 traceback，落点在翻译缓存淘汰：

```
translate_blocks → cache_put → _prune → p.unlink()
  → sitecustomize.py::_safe_path_unlink → _try_trash
  → _check_bulk_delete_guard → _exit_bulk_guard_control → raise SystemExit(1)
```

本机的 WorkBuddy 沙箱会把一批 pathlib 文件操作换成带守卫 / broker 的版本  
（`Path.unlink` / `Path.mkdir` / `Path.touch`、`os.remove` / `os.replace` / `os.chmod` …），  
守卫不通过时抛的是 **`SystemExit(1)`** —— 它继承自 `BaseException`，  
所以 `except OSError` 和 `except Exception` **都拦不住**，  
一路穿透 anyio 线程池和 FastAPI 把整次请求打成 500。

而 `translate.py` 的缓存层当时只捕 `OSError`。  
线上触发条件很具体：缓存条目涨到 `CACHE_MAX_FILES`(400) 之上，  
`_prune` 开始淘汰旧文件，第一个 `unlink` 就炸。

**修法**：缓存层统一用 `_CACHE_ERRORS = (OSError, ValueError, SystemExit)`。  
铁律是「**缓存整层都是优化，任何文件操作失败都只当这次没命中/没写成**」。  
没有直接捕 `BaseException` 的原因：`KeyboardInterrupt` 该放行，让进程能被打断。

同一颗雷在 `settings.py` 还有一处（保存 / 删除 API Key 配置），  
但那里**失败必须如实告知用户**，所以不吞异常，而是把 `SystemExit` 转成  
`RuntimeError` —— `llm_config_save` / `llm_config_clear` 已经会把它变成  
前端能显示的 JSON 错误。

> 全后端已扫过一遍文件系统写操作，只有这两处。

### 第二层：前端把纯文本 500 当 JSON 解析

FastAPI 对**未捕获异常**返回的 500 是**纯文本** `Internal Server Error`，  
而前端 `api()` 在 `!r.ok` 时直接 `r.json()`，于是抛  
`SyntaxError: Unexpected token 'I'...` —— 用户看到的就是这句解析错误，  
真正的原因被藏起来了。

**修法**：先 `r.text()`，再尝试按 JSON 解；解不出来就原样显示，并带上状态码。  
5xx 额外指引去看服务端日志（traceback 只在那里）。修好后同一场景变成：

```
HTTP 500（服务端内部错误），traceback 见服务端日志 out/_server.log：Internal Server Error
```

### 回归怎么钉的

- `scripts/probe_cache_guard.py`（17 项）：Monkeypatch pathlib 的  
  `unlink` / `mkdir` / `touch` / `os.replace` 让它们抛 `SystemExit`，  
  验证缓存层四个入口全部自己咽下去、恢复正常后功能照旧，  
  并**反向验证**换回旧异常元组时确实会穿透。  
  ⚠ 第一版教训：只写两三条缓存**跑不到淘汰分支**  
  （`files[: max(0, len(files) - 400)]` 是空切片），正向断言恒真 ——  
  必须把 `CACHE_MAX_FILES` 临时打成 0 强制走淘汰。
- `scripts/probe_api_error.py`（13 项）：用 Node 实跑从 index.html 抠出来的  
  `api()`，配假 fetch 喂「200 JSON / 500 JSON / 500 纯文本 / 400 JSON / 502 HTML」，  
  断言每条路径的消息都是人话。  
  ⚠ 抠函数不能用正则（会拦腰截断），要用花括号配对。

## 知识库：历史手账与三本复习卡片

每次点「生成手账」都会**自动落盘**到 `~/.studypad/library/`（Windows 上是
`C:\Users\<你>\.studypad\library\`，页面顶部会显示完整路径）。
刻意**不放项目目录** —— 学习数据是「这个人」的，拷贝项目或开源时不该被一起带走。

```
~/.studypad/library/
  handbooks/<id>.json   一篇手账的结构化数据（含 blocks / vocab / patterns / 译文）
  cards/words.json      生词本（跨手账聚合）
  cards/patterns.json   句型本
  cards/grammar.json    语法本
```

### 存结构化 JSON，不存 HTML 快照

导出时用现役渲染器**重新渲染**，所以以后改了版式或配色，旧手账点导出就是新样式，
不用重新上传原文、也不用再付一次大模型的钱。代价是渲染器要大改时旧数据可能渲不出来，
所以 JSON 里原样保留全部字段（含完整的 `annotations`，卡片本回查例句要靠它）。

### 三本卡片

| 本子 | 收什么 | 复习时可看到 |
|---|---|---|
| **生词本** | 所有手账里的生词，按 `lemma` 去重 | 音标 / 词性 / 释义 / **原文例句** / 出自哪几篇 / 见过几次 / 掌握度 |
| **句型本** | 所有加分句型 | 用法 + 仿写示例 + 原文例句 + 出处 + 掌握度 |
| **语法本** | 所有语法标注，按 `grammar_id` 归类 | 讲解 + 原文例句 + 出处 + 掌握度 |

掌握度三态：**○ 未掌握 / △ 模糊 / ● 掌握**，点一下就改，纯本地不调模型。
生词本还支持按关键词（单词/释义/例句）、状态、等级筛选，按最近遇到/字母/次数/掌握度排序。

### 例句来自你自己读过的原文

这是卡片本存在的理由。例句从**标注偏移回查原文那一整句**，
而不是词典自带的例句 —— 后者与用户正在读的文章毫无关系，背下来也不助于理解原文。

取不到原文上下文的情况只有一种：**复合词**（`policy-maker`、`lunch-time`、`dry-goods`
这类合成词形，原文里本来就没有这个词）。这类卡片带 `ex_from: "dict"`，
前端与导出页都会**明确标注「词典例句」** —— 不标的话用户会以为每条例句都出自自己读过的原文，
背的时候去回忆语境就白费了。（实测真实 PDF《A Piece of Red Calico》：27 词里 27 词来自原文。）

### 删除会连带回滚卡片

删掉一篇手账时，它贡献的卡片会一并移除；两篇共有的词只摘掉这一条来源、卡片保留，
而**你标记的掌握度与备注不会丢**。

这个「按来源回滚」不是可有可无的：只删 json 而不回滚，用户删掉一篇 PDF 之后，
生词本里会永久留下一批查不到出处、页面上也删不掉的僵尸条目 —— 而他根本不知道那些词从哪来。

如果卡片指向的手账文件被手工删了（不是通过界面删的），`GET /api/library/audit` 会报出来，
页面顶上出现「一键修复」按钮。正常情况下这个数组永远是空的。

### 导出

- **单篇手账**：HTML 下载 / 浏览器打印 PDF（`/api/library/<id>/html`）
- **三本卡片本**：可打印 HTML（手账纸面风格，表头每页重复）与 CSV
  （UTF-8 BOM，Excel 双击能认出中文，可直接导入 Anki）
- 导出**跟着当前筛选走**：想印「未掌握的 60 个词」，导出的就只有那 60 行

### 卡片本的可打印页

`cards_render.py` 另起了一套渲染，而不是直接打印前端页面 —— 前端页面是工具界面
（按钮、筛选器、状态标记），打印出来全是控件。卡片本要做的是**背诵清单**。
掌握度在纸上画成 `○ △ ●` 三个符号，打印出来可以手写打勾。

> **英文用清晰衬线体，不用手写体**（与纸面手账不同）。
> 手账正文用 `Segoe Script` 那类手写体是有意的观感，但知识库列表与背诵清单是
> **天天要读几十个词的工具页** —— 连笔字体下 l/1、r/v、a/d 几乎分不开
> （2026-10-15 用户反馈「根本看不清」）。中文仍用楷体，与纸面观感一致。

### 两条已固化成静态断言的排版红线

`scripts/check_inline_js.py` 会拦住下面两类问题，
并由 `scripts/probe_kb_cols.py` **反向验证它们真的会失败**：

1. **单词列不得用手写体** —— 解析 `.kb-w` 规则，`Script`/`Comic Sans`/`Brush` 一律报错。
2. **掌握列宽不得低于 10%** —— `table-layout:fixed` 下内容**不会**撑宽单元格，
   超了直接溢出到卡片边界外（用户截图正是这个）。三个按钮 + gap + padding
   至少需约 104px，容器约 1086px。

> 解析 CSS 时必须**先剥 `/* */` 注释**，并按选择器**精确**匹配规则 ——
> 直接 `re.search(r"\.kb-w\s*\{")` 会先命中
> `table.kb tr.done .kb-w{text-decoration:line-through}`（那条没有 `font-family`），
> 于是字体检查恒真。这条坑是被反向验证当场抓出来的。

### 自检不许污染用户数据

走**真服务**的自检（`smoke_api` / `verify_render_api` / `probe_live_service`）
必须给生成请求带 `no_save=true`，否则每跑一次全量回归就往用户真实知识库里灌一篇
`api-check`、`live-check` 这样的垃圾手账（实测一次就灌了 10 篇）。

⚠ **子进程设 `STUDYPAD_HOME` 没用** —— 库目录是**服务端进程**读的环境变量，
自检跑在另一个进程里。只能靠接口上的这个开关。

`probe_library_e2e.py` 相反：它**故意**要真的入库（验的就是这条链路），
所以它开头清掉自己上次的残留、结尾删干净，并断言「没留下自己的手账、没动用户的手账」。

## 页面结构：两页 + 一层公共

```
/                 制作页     上传材料 → 选等级 → 生成手账 → 预览与导出
/library          知识库页   历史手账 + 生词本 / 句型本 / 语法本
/static/common.css|.js        两页共用的基础样式与助手
```

**为什么拆**（2026-10-15）：此前所有功能挤在一个页面里 —— 首屏要同时看等级选择、
上传区、模型设置、考点面板、手账预览，外加一整套知识库。层级混乱、信息密度过高，
而且知识库的表格与制作页的表单在视觉上互相干扰。

### 入口与返回

- 两页顶栏都有 `生成手账 / 知识库` 页签，**当前页高亮**（`<body data-page>` 标记驱动，
  实现在 `common.js`，不用两处各写判断）。
- 知识库页右上角另有「← 返回制作」。
- 知识库页支持深链：`/library?tab=words` 直接落到生词本。

### 「打开历史手账」的跨页链路

拆分前，「打开」是在同一页下方展开预览。拆分后改成：

```
知识库页「打开」 → location.href = '/?doc=<id>'
                  → 制作页读 ?doc → GET /api/library/<id> → renderResult()
```

**行为与拆分前一致**：预览与导出工具栏仍在制作页（那里空间最大），
知识库页继续负责「删除 / 导出 / 打印」。

两处配套处理（不做的话用户会踩到）：
- 载入历史手账后清掉 `S.file` / `S.text` 并禁用「生成手账」——
  历史数据里没有原始文件，不清的话点「重新生成」只看到「请先选择文件」。
- 「重新开始」会先丢掉 `?doc=` 再跳转 ——
  否则从知识库进来后按「重新开始」，同一篇又被载回来，根本清不掉。

### 首屏层级

制作页首屏现在只有三件事：**选水平 → 传材料 → 生成**。

考点依据面板（原六页签、带来源徽章的那块）改为**默认折叠**：
层级上它属于「了解」而不是「操作」，此前默认展开时把「上传材料」挤出了首屏。

### 公共层的边界

`common.css` / `common.js` 里**只放真正共用的东西**：reset、配色变量、按钮/卡片/
输入框/提示条样式，以及 `$` / `esc` / `api` / `fmtDateTime` 四个助手。
任何只被一个页面用到的样式仍然留在那个页面自己的 `<style>` 里 ——
公共层变成垃圾桶比重复更难维护。

> 拆页后最容易出、也最难发现的一类错误：**公共层接线错了**。
> 比如页面引了 `common.js` 但**顺序在页面 script 之后** → `$` / `api` 还没定义
> 就跑页面脚本 → 整块脚本抛 `ReferenceError`，而其它面板看着一切正常。
> 这些都不会让任何自检变红，所以已固化成断言：

- `scripts/check_inline_js.py` 现在校验**多个页面**（`index.html` + `library.html` + `common.js`）
  的语法、id、class，并检查公共层接线（引用是否存在、顺序对不对）。
- `scripts/test_pages.py`（39 项）守住跨页链路：两页互指的入口、`/library` 路由、
  「打开」的 `?doc=` 闭环（两端必须对得上同一个 id）、以及首屏密度。

> 新增页面**必须登记到 `check_inline_js.py` 的 `page_names`**，
> 否则它的语法与 id 错配就完全没人把关 —— 而这类错误的表现
> 恰恰是「只有新功能没反应」，最难被注意到。

## 主题：白天 / 黑夜

顶栏右侧（☀ / ☾）一键切换，选择记在 `localStorage`（`studypad.theme`）里。
默认**跟随系统**：用户没有明确表态时，系统是夜间就用夜间。
按钮循环顺序是 `跟随系统 → 白天 → 黑夜 → 跟随系统`，
而不是只在明暗之间切 —— 否则「跟随系统」这个默认态就再也回不去了。

也支持 URL 参数直接进：`/?theme=dark`、`/library?theme=light`（会记住该选择）。
既能分享「看暗色长什么样」的链接，也方便自动化截图。

### 刷新不闪白

防闪烁脚本**同步内联在 `common.css` 之前**。放其后会看到「先白一下再变黑」——
那一下在夜间非常刺眼，等于功能做了但体验坏了。
它不能挪进 `common.js`：那是普通 `<script src>`，要等下载 + 解析完才跑，来不及。

### 所有颜色一律走变量

`common.css` 里是一套语义令牌（`--card` / `--ink2` / `--surface-3` / `--badge-*` /
`--num-*` …），`:root` 一套、`[data-theme="dark"]` 一套。**暗色块只覆盖变量，
不重复任何选择器** —— 这是令牌化的全部意义。

原本两个页面里有约 55 处硬编码 `#hex`，它们覆盖不到变量，暗色下就是一块块白斑，
已全部收敛。`check_inline_js.py` 有断言在盯这件事（见下）。

暗色配色不是简单反色：底色用近黑的中性灰（`#14161a`）而不是纯黑，
正文用 `#e6e8eb` 而不是纯白（对比过冲）；徽章从「极浅底 + 深字」换成
「深底 + 亮字」；`select` 的下拉箭头必须换成浅色 SVG data-uri，
否则是「功能在但几乎看不见」。

### 手账与卡片本：屏幕深色，打印白底

手账是**纸面产物**（要打印、要导出 PDF、要下载 HTML），所以：

- 预览 / 「在新窗口打开」：注入 `<html data-theme="dark">`，走暗色皮肤；
- **打印时必须逐条收回浅色** —— 媒体查询不影响选择器，
  `[data-theme="dark"]` 的覆盖在打印时同样会命中。
  少收回一条就会出现「某类批注印出来是深底白字」：既费墨，PDF 也不像样。
- 「下载手账 HTML」走的是**原始** html，不注入主题 —— 拿到的永远是白底纸面。

### 相关断言

| 断言 | 位置 |
|---|---|
| 页面 `<style>` 里不许有浅色硬编码（`@media print` 除外） | `check_inline_js.check_theme` |
| 暗色块必须覆盖 `:root` 的每一个令牌 | 同上 |
| 防闪烁脚本必须在样式表之前 | 同上 |
| 切换逻辑与 `#btnTheme` 齐全 | 同上 |
| 打印时关键元素都被收回了浅色（含反向验证） | `probe_theme_render.py` |
| 以上四条都能被破坏性样本抓住 | `probe_theme.py` |

## 已知边界

- **OCR 已接入**（RapidOCR / onnxruntime，Apache-2.0）。扫描件 PDF 与拍照图片都能解析，  
  自动判定是否需要 OCR（平均每页字符数 < 100 即走 OCR 通道），无需用户手动切换。  
  代价：首次调用要加载模型（本机实测约 20 s，之后常驻内存）。
- **许可风险已消除**。PDF 引擎用 `pypdfium2`（Apache-2.0 / BSD-3），  
  原先的 PyMuPDF 是 AGPL-3.0、会传染整个服务端，已在本轮替换掉。
- **OCR 精度边界**：RapidOCR 偶有整行识别失败，或把词间空格吃掉  
  （实测 `The Cost of Convenience` → `The Costof Convenience`）。  
  前者已被 `layout.is_garbled()` 识别并丢弃（解析结果里会报告丢弃了几行）；  
  后者不做自动拆分 —— 拆「粘连词」的规则会误伤 `YouTube` / `iPhone` 这类真驼峰词，  
  代价大于收益。
- **双栏排版已支持**：中缝检测 + 递归切栏，文字层与 OCR 共用同一套版面色重建逻辑。
- 词形还原是规则实现，不规则派生词可能漏匹配。  
  英式拼写变体（`organise → organize`）与 `-ive↔-ion`（`convulsive → convulsion`）  
  已在候选表里补上；但这些规则**必须排在候选表最后**，否则会误伤同形真词  
  （`promise → promize`）——顺序即安全边界，改 `lemmatize.py` 时不要重排。
- **补充词典要单独构建**：`data/dict/general.json` 缺失时功能静默降级  
  （六档之外的词在生词表里没有音标/词性/释义），不报错。换机器记得跑  
  `build_general_dict.py`。
- **未取到译文的句子不再配空框**：只排原文，段落末尾给一条灰色 `.tr-miss` 说明。  
  这是刻意的取舍 —— 空框堆满一页会被当成整页留白，而「哪几句没翻」用一行字说清更省地方。
- **视觉回归需要 Chrome**：`probe_pixels.py` / `probe_pagination.py` 靠无头 Chrome  
  真渲染 + 真导出 PDF。找不到 Chrome 时 `run_all.py` 会跳过这一链（不算失败），  
  但「留白」这类问题就失去唯一的视觉证据 —— 有条件就跑，别长期跳过。
- 语法识别是正则 + 启发式，非句法分析器。接入 `stanza` 可提升精度，代价是 ~500MB 模型。
- **译文缓存不区分模型**：缓存按「原文句子」哈希，换模型/换 provider 也照样命中。  
  这是刻意的 —— 同一句英文的译文本就该一样，缓存的意义是「不为同一句话付两次钱」。  
  若换了更强的模型想要更好的译文，点「清空译文缓存」即可。
- **译文是机器生成，供理解参考**，不能当作权威译本；手账页脚也标了这一点。
- **整篇译文默认只翻前 24000 字符**（约 8 页 A4）。超出部分不译并明确标注，  
  不会静默截断让人以为翻全了。需要更多可调 `translate.MAX_CHARS`。
- **产物的 CSS 是「交给外部环境渲染」的**：本机量到全对，不代表用户那边全对。  
  两个已加固的脆弱点：① CSS 变量一律带 `--sp-` 前缀（`--hl` 这类通用名会被宿主主题重定义）；  
  ② 渐变里的透明端不用 `transparent`（它就是 `rgba(0,0,0,0)`，丢 alpha 会变成不透明纯黑）。  
  改动渲染样式前先看「黑色横杠」一节，`check_render.py` 的正/反向断言会把它们拦下。
