## 一、结论先说

调研的结论是「没有一个项目完整实现设想，但每块都有成熟实现」。落到工程上，我把复用拆成**四类**，
每类对应不同的成本与法律风险：

| 复用类别 | 含义 | 成本 | 许可风险 | 本项目采用 |
|---|---|---|---|---|
| **Fork 当外壳** | 直接改别人的完整应用 | 最低 | 高（需继承许可） | ❌ 不采用 |
| **抄机制** | 读懂算法，用自己的代码重写 | 中 | 无（思想不受版权保护） | ✅ **主力方式** |
| **只用数据** | 只取词表/语料等事实性数据 | 低 | 低（需查数据许可） | ✅ 已采用 |
| **依赖调用** | 作为库/服务调用 | 低 | 中（AGPL 会传染） | 🟡 按需 |

**为什么不用 fork 外壳（拾语 shiyu / read-bridge）**：
虽然调研推荐了它们，但两者都是**面向个人阅读器**的桌面应用，形态与本产品（Web 端批量上传 + 手账导出）
差异很大。fork 意味着继承 Tauri + Rust + Vue 技术栈、继承它们的 UI 假设、并且**被 GPL 系许可约束**
（read-bridge 是 MIT 可以，但 shiyu 的功能缺口恰好在"分级标注 + 手账导出"这两块核心上）。
保留「抄机制」的做法，能用 Python 重写出更贴合本产品的实现，且许可完全干净。

    ├── xournalpp (GPL-2.0)      → 只借鉴交互设计
    ├── LinguaCafe / lector (GPL/AGPL) → 不接触

> ✅ **许可风险已清除**：本项目最初原型用的 **PyMuPDF 是 AGPL-3.0** ——
> 一旦商业化，AGPL 会要求开源整个服务端。本轮已把它彻底替换为
> **`pypdfium2`（Apache-2.0 / BSD-3）**，AGPL 传染风险归零。
>
> 替换过程中发现 pypdfium2 与 PyMuPDF 的三处行为差异，均已解决：
> 1. **没有内置的 dict/layout 分析**，须自己按字符框聚类成行 —— 见下节「版面重建」；
> 2. **`get_fontsize()` 不可靠**（18pt 报 12.0、10.5pt 报 8.6，比例不稳定），
>    改用「行内字符框高度的 90 分位」作字号代理；
> 3. **没有 OCR 兜底**，扫描件必须自接 OCR 引擎 —— 已接 RapidOCR。

## 五、实作中发现的、需要回写进开发文档的修正

这是本次开发最有价值的部分——**三个原设计在实测中被证伪**：

### 修正 1：`popcount(词表归属)` 不能当词频用 ❌

原设计（开发文档 3.4）假设「词出现在越多档词表 → 越常用」。实测证伪：

```
different  出现在 高中+四级 两档 → 被当成「中等难度」而标出
endurance  只出现在四级一档     → 被当成「四级特有词」而标出
```

但 `different` 是 421 名的超高频词，`endurance` 是 14627 名的低频词——**两者完全颠倒**。
根因是六档词表本身重叠度低（高中 3743 ∩ 四级 4544 只有 2708），popcount 分布集中在 1–3，无区分度。

**修正**：引入独立的通用词频表（google-10000-english）作为唯一可靠的「常见度」信号。

### 修正 2：必须加「词频地板」才能避免划满 ⚠️

即使有了词频，只按分数排序仍会填满预算——文章里可能没有足够多的低频词，于是
`kitchen`、`corridors` 这类基础词被补位标出。**必须设硬性地板**：

| 等级 | 词频地板 | 含义 |
|---|---|---|
| 高中 | 2000 | 比 2000 名更常见的词一律不标 |
| 四级 | 3000 | |
| 六级 | 3800 | |
| 考研 | 4200 | |
| 雅思 | 4800 | |
| 托福 | 5500 | |

### 修正 3：需要「本级新增词」信号 ✨

`kitchen` 虽然词频不算高，但**高中词表就已收录**——四级考生必然认识。
因此追加信号：**该词是否属于「更低档词表全都没收、只在本级出现」**。

```
score(target) = (0.30 + 0.70 × 词频稀有度) × (1.0 if 本级新增 else 0.45)
```

加上这三项修正后，同一篇文章的输出变得可用：

| 等级 | 荧光笔(本级词) | 红圈(超纲常见) | 蓝线(超纲生僻) | 语法标注 | 加分句型 |
|---|---|---|---|---|---|
| 高中 | 10 | 6 | 4 | 16 | 8 |
| 四级 | 7 | 5 | 3 | 15 | 8 |
| 六级 | 5 | 2 | 2 | 12 | 11 |
| 雅思 | 3 | 0 | 2 | 7 | 11 |
| 托福 | 2 | 0 | 1 | 6 | 9 |

**标注密度随等级单调下降** —— 这正是「同文不同标」的产品灵魂，且是数据驱动的。

### 修正 4：pypdfium2 没有版面分析，必须自己重建 🧱

PyMuPDF 自带 `page.get_text("dict")`，会直接给出 block / line / span 与字号；
**pypdfium2 只给到「字符框」**（`get_charbox`）。所以替换引擎的同时，
不得不自己写一层版面重建 —— 这就是 `layout.py` 的由来。

反过来说这也是好事：**扫描件 OCR 出来的也是「一堆带坐标的文本行」**，
和文字层抽取的结果是同一种东西。于是两个通道可以共用同一个 `layout.build_blocks()`，
「统一中间表示」从设计口号变成了代码事实：

```
文字层 PDF ──pypdfium2──┐
                        ├─→ List[Line] ─→ layout.build_blocks() ─→ Block[] ─→ 后续全部共用
扫描件/图片 ──RapidOCR──┘
```

实测两条通道的产出高度一致（同一篇双栏文章）：

| 输入 | 区块 | 词数 | 荧光笔/红圈/蓝线 | 语法 | 句型 |
|---|---|---|---|---|---|
| 文字层 PDF | 7 | 326 | 6 / 4 / 3 | 17 | 7 |
| 扫描件 PDF（OCR） | 8 | 314 | **6 / 4 / 3** | **17** | **7** |

### 修正 5：字号代理不能用「字符框高度的众数」📏

原实现取行内字符框高度的**众数**。实测该值在 4.80 / 5.00 / 7.30 之间乱跳，
同一段落被判成三种字号，于是 `size_shift` 触发断块 + 误判标题
（双栏页 17 个碎块，`without saying that technology itself` 被当成 h1）。

根因：pypdfium2 的 charbox 是**字形包围盒**，不是字号 ——
`prevention rather than remediation.` 以小写 x-height 字母为主 → 4.80；
`without saying that technology itself` 含 h/k/t/f/g → 7.30。

而 OCR 侧也不能用检测框高度：RapidOCR 的框**被引擎统一 padding 过**，
同一份文档的 title 与 heading 框高只差 2.6%（16.55 vs 16.13），真实字号却差 40%。

**最终方案：用「行宽 ÷ 等效字符数」的平均字符宽度做字号代理**（`Line.avg_width`）。
它只跟字宽有关、与升降部无关，且跨通道一致：

| | 文字层 | OCR |
|---|---|---|
| heading / 正文 | 1.43 | 1.63 |
| title / 正文 | 2.07 | 2.16 |

四个比值全部落在阈值 1.75 的两侧（最小余量 0.12），title 与 heading 分级
在两条通道上第一次完全一致。

> 顺带记录：文字层「字符框高度 p90」的逐行波动确实更小（rsd 1.1% vs 2.9%），
> 但它是**通道内**更稳、**跨通道**不可比。判标题要的是跨通道可比，所以选了 avg_width。

### 修正 6：中缝检测的候选点不能先 round ⚠️

`_largest_gutter` 原本把所有行的 x0/x1 去重后当候选切分点。
但 OCR 的框带小数：左栏最右 `x1 = 214.04`，`round(v, 1)` 后变成 `214.0`，
于是判断 `x1 <= 214.0` 为**假** —— 这条行既不算左栏也不算右栏，
`cross = 1 > 0`，整条中缝被否决，函数返回 `None`。

后果：双栏被当成一栏按 y 排序，同一高度的左右两栏行相邻、`gap ≈ 0`，
直接被拼成一行（`Some scholars argue that the second Policymakers should invest…`）。

**改为**：在 `[0.24·W, 0.76·W]` 区间内均匀扫描 65 个候选点，
按「跨界行数最少、左右行数最均衡」选优，并把归类改用**行中心点**判定，
允许 10% 以内的跨界行（栏宽不等、标点越界、OCR 抖动都会造成少量跨界）。

## 六、下一步建议

1. ~~**接 OCR**~~ ✅ **已完成**：RapidOCR（Apache-2.0）+ onnxruntime，
   扫描件与图片全通，纯图片 PDF 自动判定并切 OCR 通道。
   （不用 PaddleOCR 的原因：`rapidocr-onnxruntime` 不支持 Python 3.13，
   而新版 `rapidocr` 已切到 onnxruntime 后端，Windows + 3.13 可直接装、无需 paddlepaddle。）
2. ~~**换掉 PyMuPDF**~~ ✅ **已完成**：`pypdfium2`，AGPL 风险归零。
3. **建黄金数据集**：请英语老师标注 20 篇文章 × 6 档，用开发文档 16.2 的指标评估当前规则引擎，
   再决定哪些环节值得上 LLM。
4. **验证 LLM 增强的边际收益**：当前 LLM 只重写语法讲解。需要用 A/B 测出
   「规则讲解 vs LLM 讲解」在可用性评分上的差距，再决定预算。
5. **补 `correction` 标注类型**（Gramformer）——对应「用户自己写的作文 → 涂改纠错」这条产品线。
6. **OCR 后处理增强**：修「词间空格被吃掉」（`The Cost of Convolience` → `The Costof Convenience`）。
   难点在于拆分规则会误伤 `YouTube` / `iPhone` 这类真驼峰词 ——
   可行方向是「拆分后每段都必须在词表内」才拆，而不是纯靠大小写边界。
